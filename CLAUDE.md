# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

MultiPie is a Python library (Python >= 3.12) that provides a database of crystallographic point groups and space groups, both ordinary and magnetic (PG/SG/MPG/MSG). It builds Symmetry-Adapted Multipole Bases (SAMB) and tight-binding models from that database. Structures and SAMB figures are written as QtDraw files (`.qtdw`), and PDF output goes through LaTeX (TeXLive, optional).

## Branch workflow

- `main` is the default branch and is used for releases. Every PR branches from `develop` and targets `develop`.
- After merging a PR into `develop`, delete the feature branch, then run the test suite on the updated `develop`.
- The maintainer opens and merges the `develop` → `main` PR by hand. Never delete `develop`.
- A GitHub release whose tag is `v` + `multipie.__version__` (e.g. `v2.4.1`) publishes the package to PyPI (`.github/workflows/release.yml`). The version is set in `multipie/core/multipie_info.py`.

### Ver.3 (`develop-v3`)

- `develop-v3` is the development line of Ver.3 (the group database of MultiPieGen; version `3.0.0.devN`), while `develop` and `main` stay Ver.2 (2.5.x). Never delete `develop-v3`.
- Work for Ver.3 branches from `develop-v3`, and its PRs target `develop-v3` (`gh pr create --base develop-v3`). After merging, delete the feature branch and run the test suite on the updated `develop-v3`, as for `develop`.
- Fixes for Ver.2 go to `develop` as usual. Bring them into Ver.3 by merging `develop` into `develop-v3` (a PR from `develop`, or `git merge origin/develop` on a branch from `develop-v3`). Do not rebase `develop-v3` or force-push it, since others test it.
- Test Ver.3 in an environment separate from Ver.2. QtDraw 3.4 (QtDraw's branch `develop-v3.4`) works with Ver.3 (`multipie~=3.0.dev0`), and QtDraw 3.3 on PyPI with Ver.2 (`multipie~=2.5`), so the `dev` extra does not include QtDraw. To write `.qtdw` files with Ver.3, install QtDraw 3.4 after MultiPie: `pip install "git+https://github.com/CMT-MU/QtDraw.git@develop-v3.4"`. Install MultiPie Ver.3 itself with `pip install "git+https://github.com/CMT-MU/MultiPie.git@develop-v3"` (also on Windows, since the data files have no `:` in their names).
- For testers, a pre-release version (e.g. `3.0.0a1` in `multipie_info.py`) can be released from `develop-v3` with the tag `v3.0.0a1`. A GitHub release marked as a pre-release uploads to TestPyPI only (`release.yml`); one not marked so uploads to PyPI, where pip still installs a pre-release version only with `--pre`. The maintainer decides which, and when `develop-v3` goes into `develop` for the release of Ver.3.

## Commands

```bash
pip install -e ".[dev,tetrahedron]"        # dev install (tetrahedron = optional libtetrabz for DOS)
pytest -n auto                              # all tests in parallel (testpaths = tests)
pytest tests/test_model.py::test_model_files  # a single test
MPLBACKEND=Agg pytest -n auto               # headless, as in CI
black .                                     # formatter; line length 130 (pyproject.toml)
make -C docs build                          # Jupyter Book docs -> docs/_build/html; {code-cell} pages run at build (cached)
mp_create model_in.py                       # CLI: create model(s); `mp_create -i` prints the input template
mp_analyze model_ctrl.py                    # CLI: analyze model(s) from control file(s)
```

CI (`.github/workflows/test.yml`) installs the package non-editably on ubuntu and macOS with Python 3.12 and 3.13. It runs the tests from outside the checkout, so they must import the installed package rather than the source tree. As a result, anything the package needs at runtime has to be covered by `package-data` in `pyproject.toml`.

## Architecture

The public API is lazily imported in `multipie/__init__.py` (`Group`, `MaterialModel`, `ModelAnalyzer`, `create_model`, `analyze_model`). The same file defines the namedtuple types used throughout the package (`PGMultipoleType`, `RepSiteType`, `CellBondType`, `SAMBType`, ...). Logic lives in `multipie/core/`, and most of the heavy lifting is in the helper modules under `multipie/util/`.

The pipeline has three layers:

1. **`Group`** (`core/group.py`) is a read-only view of precomputed group data. A group is identified by a tag such as `PG:1-47`, `SG:1-230` (or a bare integer), an MPG `PG.no.ID`, an MSG BNS id, or a Schoenflies symbol. Data loads from pickles in `multipie/binary_data/{PG,SG,MPG,MSG}/` and `info.pkl` (about 20 MB, generated by MultiPieGen) through `BinaryManager` (`util/util_binary.py`). On loading, `_set_samb_dict` turns the multipole data into `Dict` and attaches to each atomic and cluster SAMB the expression of its harmonics in the PG data (the binaries hold none). Loads are cached per process (`Group.clear_cache()`). NumPy arrays are shared and read-only, while dicts and lists are copied for each `Group`. `Group` provides symmetry operations, Wyckoff positions, harmonics, atomic, cluster and combined SAMB, and response tensors.
2. **`MaterialModel`** (`core/material_model.py`, also a `BinaryManager`) turns a *model input* dict into a model. `analyze()` finds Wyckoff sites and bonds, builds the cell sites and bonds, and builds the atomic, cluster and combined SAMB. `save()`, `save_view()` and `save_pdf()` then write `<topdir>/<model>/<model>.pkl`, a `.qtdw` file and a PDF. The input keys and their defaults are in `core/default_model.py`, which is also what `mp_create -i` prints.
3. **`ModelAnalyzer`** (`core/model_analyzer.py`) reads a *control* dict (defaults in `core/default_control.py`) and runs in one of three modes:
   - `samb`: builds a tight-binding Hamiltonian from SAMB weights `z_j` on a saved model `.pkl`.
   - `wannier`: reads Wannier90 output (`.win`, `.nnkp`, `_hr.dat`, `_wsvec.dat`) through `util/util_wannier.py`.
   - `symcw`: combines the two modes above by decomposing the Wannier Hamiltonian onto SAMB.

   It then computes physical quantities: band dispersion along a seekpath k-path, DOS (Gaussian or tetrahedron), the Fermi energy from filling, fat bands, local operators, k-multipoles, and user callbacks (`callback_k_path` / `callback_k_full`). Results go to `<topdir>/<model>/output/`, including gnuplot scripts.

`core/cmd.py` (`create_model`, `analyze_model`) wraps layers 2 and 3. The click CLIs in `scripts/` are thin front ends to it.

Input and control files are Python files holding exactly one dict literal. They are read with `util.util.read_dict` and `read_dict_file`, never executed as code. Output dict files are formatted with black if it is installed (`do_black`). Missing keys are filled in from the defaults with `deep_update`, and unknown keys are rejected by `check_dict_keys`.

## Data, examples, and tests

- `docs/src/examples/` holds the worked example models (`*_in.py`, `*_ctrl.py`, and their generated outputs). `tests/test_model.py` uses the graphene example as a regression fixture.
- `tests/data/materials/` holds the model inputs of SrVO3, MoS2 and Te. `tests/test_materials.py` checks them by basis-independent properties (number of SAMB, symmetry and degeneracies of the bands with random weights), which stay valid when the group database changes. The same inputs are the examples of `docs/src/materials.md`; regenerate its outputs (models, SAMB tables, figures) with `python docs/src/examples/materials/create_examples.py` after a change of the database or of the controls in that directory.
- The docs have a User Guide (`docs/src/guide.md`, with the Japanese version `docs/src/guide/users_guide_ja.md`) and the changes from Ver.2 (`docs/src/changes.md`, with `docs/src/changes_ja.md`); the Japanese versions are orphan pages. Keep the two languages in sync, and prefix the MyST labels of the Japanese pages with `ja-` (labels are global).
- **Do not modify `multipie/binary_data/` by hand.** It holds the group database generated by MultiPieGen, a separate repository, and is replaced only by `python tools/sync_binary_data.py <MultiPieGen checkout>`, which copies `multipiegen/binary_data` and records the source commit in `multipie/binary_data/SOURCE.txt`. The file of a group has `_` instead of the `:` of its id (e.g. `PG/PG_32.pkl` for `PG:32`; `group._group_file`), as git on Windows cannot check out a file name with `:`. Only the maintainers update it; if a task seems to need a change there, stop and ask. The group PDFs are also generated by MultiPieGen. The "Group information" entry of `docs/_toc.yml` links directly to the Group Information of MultiPieGen (https://cmt-mu.github.io/MultiPieGen/src/group_info.html); the same URL is used in `overview.md`, `guide.md`, `changes.md`, `changes_ja.md` and `guide/users_guide_ja.md` (`git grep` it to change it).
- There is no `others/` in the repository. `others/uc/` and `others/doc_src/` are gitignored for local material only.
- Every source file starts with the MPL-2.0 SPDX header. Earlier versions, up to 2.3.4, were released under MIT.
